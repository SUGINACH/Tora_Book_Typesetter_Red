## tools/run-tests.js — runner גילוי הבדיקות (D-110)

`npm test` ו-`npm run test:regress` מפעילים אותו (במקום שרשרת `node a && node b` ב-`red-build/package.json`). הוא מגלה כל `red-build/tests/**/*.test.js`,
מריץ כל קובץ כ-`node <נתיב>` מתוך `red-build/` (אותה סביבה, אותן שורות סיכום ל-CI), וכושל על בדיקה שקטה (בלי שורת סיכום), על "כשל שקט"
ועל בדיקה יתומה (קובץ שנראה כבדיקה אך אינו `*.test.js`). **הוספת בדיקה = יצירת קובץ `*.test.js`, בלי לערוך package.json או workflow.**
`--list`/`--list-json` (התכנית), `--only <תת-מחרוזת>` (פיתוח), `--bail` (עצירה בכשל ראשון), `--json <file>`, `--check` (שומר-כיסוי בלבד) — ראו `--help`.
`run-baseline.js` לוקח ממנו את רשימת הצעדים; בעץ ישן, לפני ה-runner, הוא חוזר לפירוק השרשרת הידנית.

### עדויות הבדיקות אינן מלכלכות את העץ (R-4)
בדיקות הייצוא/הקבלה/הגופנים (`s12-export`, `s13-acceptance`, `real-fonts`, `s53-dp-notes-export`, `d89-visual-fixes`) והסריקה (`scan-control-triggers`) כותבות PDF/JSON ל-`red-build/tests/artifacts/` —
תיקייה **במעקב git** — ובכל ריצה חלק מהקבצים משתנים (שעוני תזמון ב-`s13-perf.json`, חותמות PDF, גרף קריאות מתיישן): `npm test` הותיר עץ מלוכלך, ו-baseline/מיזוג נמדדו על עץ שמשתנה תוך כדי.
מעכשיו ה-runner מגדיר לילדים `RED_ARTIFACTS_DIR=<תיקייה זמנית>` (הבדיקות מקבלות את התיקייה מ-`artifactsDir()` ב-`tests/harness.js`), והתיקייה נמחקת בסוף. **שומר-סחף** משווה (sha256) את `tests/artifacts` לפני/אחרי:
בדיקה שכתבה לשם ישירות — נוסף/שונה/נמחק קובץ — מכשילה את ההרצה עם שם הקובץ, גם אם כל הבדיקות ירוקות.

| רוצים | עושים |
|---|---|
| ריצה רגילה / CI | `npm test` — כלום לא ייכתב לעץ (ברירת מחדל) |
| לרענן בכוונה את העדויות שבמעקב (למשל PDF קנוני חדש לבדיקת עין) | `npm test -- --write-artifacts` (בלי הפניה ובלי שומר) ואז לבדוק `git diff` ולבצע commit מכוון |
| לבדוק את העדויות שהריצה הפיקה | `npm test -- --keep-artifacts` (הנתיב מודפס); ריצה **כושלת** שומרת את התיקייה אוטומטית |
| תיקייה משלכם | `RED_ARTIFACTS_DIR=/path npm test` (נשמר כמות שהוא) |
| קובץ בדיקה בודד | `node tests/e2e/s12-export.test.js` — כותב ל-`tests/artifacts` כמו תמיד (הפניה קיימת רק דרך ה-runner / המשתנה) |

בדיקה חדשה שכותבת עדות חייבת לקחת את התיקייה מ-`artifactsDir()` ולא לחשב נתיב בעצמה — אחרת השומר יכשיל אותה. `run-baseline.js` מריץ את הסוויטה עם אותה הפניה (`--keep-artifacts` שלו מכבה אותה),
ולכן `manifest.trackedDrift` צפוי להיות ריק; הוא נשאר רשת ביטחון (עץ שקדם ל-R-4, בדיקה שכותבת ישירות).

## impact.js — אימות תיקון מנוע בפקודה אחת

```bash
git worktree add --detach /tmp/red-base origin/main          # base
git worktree add --detach /tmp/red-cand <commit-עם-התיקון>    # מועמד (באנדלים נבנו מחדש: node tools/build-worker-bundle.js)
node tools/baseline/impact.js --base /tmp/red-base --cand /tmp/red-cand --details
```

ברירת מחדל: `approx` (בלי גופנים) על כל הקורפוסים (`canonical`, `no_long`, `mid_long`, `long`, `long_no_paren`, `very_long`, מסמך הבדיקה הקבוע `generator`), ו-`real` / `real+stretch` (גופנים אמיתיים, כמו צינור ה-parity) על `no_long` ו-`generator`. כ-1–2 דקות.
`--modes`, `--docs` מצמצמים; `--expect-neutral no_long,canonical` נכשל (קוד 4) אם אחד המסמכים האלה השתנה בכלל — לתיקון שאמור להיות ניטרלי ל-parity; `--json out.json` שומר את כל המדידות.

**קוד יציאה:** `0` אין רגרסיה · `3` רגרסיה · `4` מסמך `--expect-neutral` השתנה · `2` שגיאת הרצה.

**מה נחשב רגרסיה (קוד 3):** הערות-שוליים **אבודות**, **כפילות** באותו עמוד, **סדר** הערות, **כיסוי הערות לפי עמוד** (עמוד שיש בו שורות של פסקה נושאת-הערה בלי יחידה של אחת מהערותיה); **הערות-סיום** שאבדו / נפלטו כפולות או שגויות / שונה סדרן / סמניהן כפולים; **הערות-צד** (`כותרת 7`) שאבדו / בעמוד שגוי / כפולות / עם טקסט זר; **מספר טוקנים** של אותו מקור ששונה — כל אלה לפי ספירה שעלתה; `contentPreserved` שהפך ל-false, מילים חסרות (`contentStats.missingCount`) או `content-loss` ב-`ledger` שעלו; ו**רפאים** — אך רק כשה-base נקי מרפאים בכל המטריצה. כשה-base מכיל רפאים (כמו לפני תיקון R-04) הזזת עימוד מזיזה מופעי רפאים בלי קשר לתיקון הנבדק, ולכן עלייה ברפאים מדווחת כ-`~` (תנודה) בלבד; `--details` מראה אילו רפאים נוספו/נעלמו.

**הערות-סיום והערות-צד מול שורות המקור** (אורקל `tests/regress/lib/source-oracle.js`: `noteLinesOf` / `censusNotes` / `compareNoteLines`). הערות-סיום מושוות כמולטי-סט של טקסטים (בלי תלות בעמוד), ולכן נבדקות תמיד: בשורת הדוח `סיום-אבודות 52→0` — **זה האופן שבו תיקון R-05 נראה בדוח עצמו**; `--details` מפרט איזו הערה (לפי ראשית הטקסט) אבדה/שבה/כפולה. הערות-צד תלויות באינדקס הפסקה הבעלים, ולכן נבדקות **רק כשמודל המקור מיושר לטוקני המנוע** (מספר טוקנים שווה, בניסיון שני עם `metaAnywhere` — O-6). מסמך לא מיושר מוצג `צד-הפרות לא נבדק` ובהערה בסוף הדוח (לעולם לא "תקין"; כיום: `long_no_paren`), ושינוי במספר הטוקנים בין העצים הוא רגרסיה בפני עצמו (פענוח המקור השתנה — גם כשהמודל "מתיישר מחדש" למודל האחר). הפרות שכבר קיימות ב-base (R-05 ב-`generator`; O-5 — 38 הפרות הערת-צד ב-`long`/`very_long`) אינן רגרסיה — רק עלייה, וירידה (תיקון) אינה מסומנת.

**בקרות שליליות:** `tests/regress/lib/impact-mutations.js` הוא קטלוג של 13 מוטציות על תוצאת מנוע (הערת-סיום שנעלמה / כפולה / בסדר שונה / בסמן כפול, הערת-צד שנעלמה / כפולה / בעמוד שגוי / בטקסט זר, טוקן עודף, `content-loss`, מילים חסרות, ו-issue שאינו אובדן תוכן — שאסור לסמן). כל מוטציה מצהירה אילו הודעות הכלי חייב להפיק, ומורצת גם בתוך התהליך וגם מקצה לקצה על עץ מוטנט (`IMPACT_MUT`) — כך אי אפשר שמדד ימות בלי שבדיקה תיכשל. (בגרסה קודמת של הכלי שני מדדי שמירת-התוכן נקראו משדות שגויים והיו 0 תמיד; הקטלוג נוסף כדי שזה לא יחזור.)

**מה הכלי לא קובע:** אם שינוי עימוד רצוי. "עמ' שונו" הוא חתימת עמוד שלמה (כולל עמודים שזזו בעקבות שינוי קודם ומפת תוכן). `layoutHash` אינו כולל את אזור ההערות — שינוי בהערות בלבד לא ישנה אותו אבל ישנה את חתימת העמוד.

**למה זה קיים:** הסוויטה, ה-hash הקנוני וה-parity לא תפסו תיקון R-04 ראשון שהוציא גם הערות חוקיות של פסקה שנחתכה בין עמודים (very-long 836→838 עמ', כיסוי 1→46). הכלי תופס זאת (נבדק; ראו `tests/regress/impact-tool.test.js`, כולל בקרה שלילית מקצה לקצה על עץ מוטנט).

**הגדרות המצבים** משוכפלות מ-`tools/layout-parity/run-ours.js` (הנתיב החי) ב-`workerRun` — אם הצינור החי משתנה יש לעדכן גם שם. המסמכים והאורקל נלקחים תמיד מהעץ שבו הכלי יושב; רק המנוע נטען מכל עץ.

## adjacency-scan.js — סריקת סמיכות מקור→פלט (שער 9)

```bash
node tools/baseline/adjacency-scan.js --modes approx,real,real+stretch                      # העץ של הכלי: כל הזוגות (17×17) בכל המצבים
node tools/baseline/adjacency-scan.js --tree /tmp/red-cand --arity 3 --offsets 10,160,310   # עץ מועמד; שלשות (≈38 אלף מסמכים תקינים)
node tools/baseline/adjacency-scan.js --atoms E,S,B,G --arity 3 --list 100 --json out.json  # תת-אלפבית ופירוט
```

**מתי:** לפני מיזוג תיקון/שינוי מנוע שנוגע בטוקניזציה, בלקסר, בהערות או בכותרות — ובכל פעם שמוסיפים אטום מבנה. R-05 (שורות `הערת סיום -` רצופות דורסות זו את זו) נמצא ב*סמיכות* של שני מבנים ולא נתפס שנים, כי איש לא ניסה את הצירוף;
הבדיקה הקבועה (`tests/regress/adjacency-matrix.test.js`, ≈6 שניות, בכל PR) מריצה תת-קבוצה ב-approx, והכלי הזה — את הסריקה המלאה בכל המצבים.
`--tree <שורש-checkout>` טוען את *המנוע* מהעץ הנתון; האורקל ומחולל המסמכים — מהעץ שבו הכלי יושב (כמו `impact.js --base/--cand`). להשוואה בין שני עצים מריצים על כל אחד ומשווים את שורות הסיכום (או קבצי `--json`).
כל מסמך עובר קודם את שער D-100 *של המוצר* (שרשרת כותרות לא עולה / בלי פסקה — `typeset()` דוחה אותם בכוונה); מסמכים שנדחו נספרים ומדווחים, לא נבדקים.

**מצבים:** `approx` (`legacyTypeset`, בלי גופנים) · `real` (`typeset()` עם גופנים אמיתיים) · `real+stretch` (כמו `real` + `RED_ENABLE_STRETCH_RECLAIM=1`, `RED_RECLAIM_COMPRESS_MAX=20`, כצינור ה-parity).
מתגי ה-stretch הם **קבועי-מודול** של המנוע — נקראים בטעינה הראשונה של `legacy-imud-flow.js`, ו-`pipeline.js` טוען אותו עצלנית. לכן הספרייה טוענת לכל מנוע מופעי מודולים פרטיים תחת סביבה מפורשת: המצב נקבע לפי שמו בלבד — לא לפי סדר יצירת המנועים בתהליך ולא לפי סביבת התהליך
(`adjacency-matrix.test.js` מוכיח שהפלט של `real+stretch` שונה מ-`real` ושאין זליגה ביניהם). ב-`impact.js` כל מצב רץ בתהליך נפרד, ולכן הבעיה אינה קיימת שם.

**קוד יציאה:** `0` אין הפרה לא-מוסברת ואין מחלקה במצב חלקי · `3` יש (רגרסיה / ממצא חדש / תיקון חלקי) · `2` שגיאת הרצה או ארגומנטים. שורת הסיכום: `ADJACENCY-SCAN OK|FAIL — tree=… modes=… arity=… docs=… unexplained=…`.

**מחלקות הסבר:** הפרה "מוסברת" רק אם המסמך שייך (לפי מבנה *המקור*) למחלקה מתועדת ורק בקודי ההפרה של אותה מחלקה — `R-05`: `ENDNOTE_LOST`; `O-8`: `CONTENT_PRESERVED`+`LEDGER_LOSS`
(ראו `red-build/tests/fixtures/regress/README.md`). מחלקה אחידה: כל מסמכיה הטהורים מראים את הבאג או אף אחד — מצב חלקי (למשל תיקון שמטפל ב-`E→E` ולא ב-`E→כותרת→E`) נכשל כמו הפרה לא-מוסברת.
**בדיקות הכלי:** `tests/regress/adjacency-scan-tool.test.js` — כולל בקרות שליליות מקצה לקצה על עץ מנוע מוטנט (אובדן הערת-סיום בכל מסמך; אובדן רק במסמך הראשון = תיקון חלקי שכל הפרותיו מוסברות ובכל זאת הכלי נכשל).
